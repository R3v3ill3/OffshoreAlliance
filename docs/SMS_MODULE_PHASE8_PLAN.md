## Objectives

1. **(§A, decision 1)** SMS becomes a first-class campaign header action. `campaign-detail-header-bar.tsx` gains a `CreateSmsOrchestrator` button and collapses **Build list / Add assessment / Task management** into one **Build** dropdown, leaving three "Create …" actions (Phone / Email / SMS) plus Actions. Build list stays a *toggle* bound to `?buildList=1` — inside the menu it becomes a `DropdownMenuCheckboxItem` (`role="menuitemcheckbox"` + `aria-checked`), the menu-correct equivalent of its current `aria-pressed`.
2. **(§A, decision 2)** A dedicated route family opens: **`/campaigns/[id]/sms/setup`** — the first `src/app/(dashboard)/campaigns/[id]/sms/**` segment in the codebase. `CreateSmsOrchestrator` mirrors `CreatePhoneCallOrchestrator` exactly (a `Link` wrapper, no dialog). `chat/[sessionId]` is Phase 10.
3. **(§B/§A, decision 3)** `SmsPathwayPicker` — **Blast / Chat / Survey**, structurally cloned from `src/components/phone/orchestrator/PathwayPicker.tsx`. **Chat renders but is disabled** ("Coming in a later release") and is *not* routed to the inbox as a stand-in. Blast and Survey work end to end, with and without a pre-attached cohort.
4. **(§B)** `sms` becomes a Build List purpose: `BuildListPurpose`, `PURPOSE_OPTIONS`, `handlePurposeChange`, the `FireBar` icon map, and both worker-lists route validation arrays. The fire path routes through the pathway picker instead of jumping straight to the composer.
5. **(§B)** An **SMS contact-readiness warning**: `workers.phone_e164` present **and** `workers.sms_opt_out = false`, counted and rendered as "N without a mobile, M opted out" before the organiser fires. Requires two new columns on the build-list items select.
6. **(§B, decision 4)** **Per-channel re-fire.** `fire/sms` stops writing `fired_draft_id`; each fire route gains a per-channel already-fired guard; and the build-list UI stops hiding fired lists so a second channel can actually be fired.
7. **(§D, decision 11)** **Per-question assessment targeting**: nullable `sms_survey_questions.activity_id`, `COALESCE(question.activity_id, survey.activity_id)` at the single rating-bearing interaction stamp in `src/lib/sms/survey-runtime.ts`, a per-question target select in `SmsSurveyEditor`, and campaign-coherence validation mirroring the existing survey-level rule.
8. **(§D)** **Inline assessment creation** in the survey editor: `CreateAssessmentDialog` mounted from `SmsSurveyEditor` with `lockKind="assessment"`, invalidating `['sms-survey-activities', campaignId]` **as well as** its own `['campaign-activities', campaignId]`, and auto-selecting the created `activity_id`.

Out of scope: workstream C (`<AudiencePicker>`, manual entry, CSV/XLSX import) is Phase 9; workstream E (chat session model, board, realtime) is Phases 10–11; workstream F (source taxonomy split, SMS reporting) is Phase 12. `record_call_attempt` still writes `p_source := 'call_outcome'` — a Phase 12 problem, untouched and uncontradicted here. All Phase 1–6 behaviour and tests preserved.

## The three exact chains

### Chain A — the SMS entry path (no writes)

`CampaignDetailHeaderBar` (`src/components/campaigns/campaign-detail-header-bar.tsx`, `actionButtons` lines 92–165) → **`CreateSmsOrchestrator`** (`src/components/sms/CreateSmsOrchestrator.tsx`, new) → `next/link` `Link href="/campaigns/[id]/sms/setup"` → **`src/app/(dashboard)/campaigns/[id]/sms/setup/page.tsx`** (new) → `SmsPathwayPicker` → client-side navigation only.

Decisions inside the chain:

- **A `Link`, not a dialog.** `CreatePhoneCallOrchestrator` (lines 30–45) and `CreateEmailOrchestrator` (lines 27–42) are both `trigger ? <Link href>{trigger}</Link> : <Button asChild><Link/></Button>`, with a legacy ignored `defaultOpen` prop. `CreateSmsOrchestrator` is a byte-for-byte structural clone with `href = /campaigns/${campaignId}/sms/setup` and a `MessageSquare` icon. Props `{ campaignId: number | string; trigger?: React.ReactNode; defaultOpen?: boolean }` for symmetry.
- **The header chrome is free.** `src/components/layout/header.tsx` lines 44–58 renders `CampaignDetailHeaderBar` for every path where `isCampaignDetailRoute(pathname)` is true, and `getCampaignIdFromPath` (`src/lib/campaign/campaign-detail-routes.ts` lines 19–26) only excludes the segments `new`, `email-wizard`, `soc-wizard`, `phone-wizard`. `/campaigns/[id]/sms/setup` therefore inherits the header, the resume banners and the Build dropdown with **no routing changes**. Verified, not assumed.
- **No `page.tsx` layout file is added** — `src/app/(dashboard)/layout.tsx` is the only layout in the group and already provides the shell.

### Chain B — the fire → pathway → artifact path (the only chain that writes)

`BuildListPanel` `FireBar` (`src/components/campaigns/wall-chart/build-list-panel.tsx` lines 566–625) → `onFire` (lines 269–292) → `useBuildList().fire` (`use-build-list.ts` lines 332–383, `POST /api/campaigns/[id]/worker-lists/[listId]/fire/${pathway}`) → **`POST …/fire/sms`** in **prepare mode** (no body) → `{ redirect_to: "/campaigns/[id]/sms/setup?worker_list_id=<lid>", readiness: {…} }` → `router.push` → **`/campaigns/[id]/sms/setup`** → `SmsPathwayPicker` → per pathway:

| Pathway | Continuation | Writes |
|---|---|---|
| **Blast** | `POST …/fire/sms` with `{ pathway: 'blast' }` → today's route body verbatim (`campaign_comms_drafts` shell → `sms_lists` → `sms_list_items` with opt-out/no-phone screening → `total_items` → draft↔list link → mark the worker list fired) → `redirect_to: /campaigns/[id]?tab=outreach&sub=sms&sms_list=<sms_list_id>` | `campaign_comms_drafts`, `sms_lists`, `sms_list_items`, `campaign_worker_lists` (`status`, `fired_sms_list_id`, `fired_at` — **not** `fired_draft_id`) |
| **Survey** | client-side navigation only → `/campaigns/[id]?tab=outreach&sub=sms&sms_view=surveys&survey_source_list=<lid>` → `SmsSurveysPanel` opens `SurveyEditorSheet` in create mode with the source list pinned → the normal `POST /api/campaigns/[id]/sms-surveys` carries `source_worker_list_id` | `sms_surveys.source_worker_list_id` at survey-create time. Nothing at fire time. |
| **Chat** | disabled card, no continuation | none |

Decisions inside the chain:

- **`fire/sms` becomes two-mode on one route, and prepare mode writes nothing.** Today (`fire/sms/route.ts`) the route creates the draft, the `sms_lists` row, the items, marks the list fired and redirects **straight to the composer** (line 187). Splitting it into `prepare` (no `pathway` in the body → validate campaign ownership + non-empty list, compute readiness counts, return the picker URL) and `pathway:'blast'` (the existing body, unchanged except the redirect target and the `fired_draft_id` removal) keeps one route, one validation path, and — critically — means **abandoning the picker leaves no artifacts**. Today an abandoned fire leaves a fired worker list plus an orphan draft blast. `pathway:'chat'` returns 400 `{ error: 'The SMS chat workspace is coming in a later release' }` as defence in depth behind the disabled card.
- **Rejected: creating the `sms_lists` row before the picker** (the literal `fire/phone` shape, which creates `call_lists` + `phone_call_actions` at lines 58–132 before redirecting to `/phone/setup?action_id=`). A `call_lists` row serves *both* phone pathways, so creating it early is honest. An `sms_lists` row is a **blast** artifact only — Survey freezes its audience from a worker list at open time (`sms-surveys/[surveyId]/actions/route.ts` lines 256–280) and Chat will use a session table (Phase 10). Creating one up front would leave a phantom draft blast in the Blasts tab every time an organiser picks Survey, and there is no `DELETE` handler on `/api/campaigns/[id]/sms-lists/[listId]` to clean it up (only `GET` and `PATCH` exist).
- **Rejected: a `fired_survey_id` column.** The Survey pathway's link is the *reverse* pointer `sms_surveys.source_worker_list_id`, which the migration adds anyway. Keeping the migration to two columns is the brief's instruction.
- **The Survey pathway does not mark the source list `fired`.** `fired` means "a channel artifact was created from this cohort"; a draft survey merely *references* the cohort and freezes its own roll later. Recorded as an in-phase decision below.
- **The header entry has no cohort.** With no `worker_list_id`, Blast → `?tab=outreach&sub=sms&sms_view=blasts&new_blast=1` (opens the existing `NewBlastSheet`, whose single audience Select is Phase 9's target) and Survey → `?tab=outreach&sub=sms&sms_view=surveys&new_survey=1`. The whole (pathway, workerListId) → target mapping is a pure function and is unit-tested (work item 9).

### Chain D — the per-question assessment target path

`SmsSurveyEditor` per-question **"Write to"** select → `SurveyEditorQuestion.activity_id` → `toQuestionInputs` (lines 116–142) → `POST/PATCH /api/campaigns/[id]/sms-surveys[/surveyId]` → `validateSurveyQuestions` (pure) + a per-question campaign-coherence check → `insertSurveyQuestions` (`src/lib/sms/survey-authoring.ts` lines 13–53) → `sms_survey_questions.activity_id` → **member answers** → `processSurveyInbound` (`src/lib/sms/survey-runtime.ts` lines 494+) → `INSERT sms_interactions` with `activity_id = COALESCE(question.activity_id, survey.activity_id)` (line 606 today) → the EXISTING `trg_sms_to_rating` → `record_assessment_event(source 'sms', event_id NULL, phase 'actual')` → `campaign_activity_ratings`.

Decisions inside the chain:

- **The stamp site is singular and already loads what it needs.** `loadSurveyBundle` selects questions with `select("*")` (lines 80–81), so `activity_id` arrives with no loader change. The only rating-bearing insert is at lines 601–618, gated by `isRatingAnswer` at lines 582–585 (`parsed && currentQuestion.write_rating && survey.activity_id != null`). That gate becomes `targetActivityId != null` where `const targetActivityId = currentQuestion.activity_id ?? survey.activity_id`, and both `activity_id` (line 606) and the `cta_response` / `maps_to_*` decision use it. Making the *gate* COALESCE-aware (not just the column) is deliberate: a question-level target with no survey-level target must still write, even though the UI cannot currently produce that state.
- **The `cta_response` trap survives unchanged.** `fn_sms_to_rating` treats `cta_response` as a binary value whenever `activity_id` is set, so non-`write_rating` answers keep carrying the activity link with all three value fields NULL (Phase 4 plan §write path). The COALESCE changes *which* activity is linked, never *whether* values ride along.
- **The second interaction insert also moves to COALESCE.** `processBallotPostCompletion`'s `reject_locked` audit row (lines 1011–1027) stamps `survey.activity_id` with all three value fields NULL. It becomes `firstQuestion.activity_id ?? survey.activity_id` for link coherence. Zero rating risk (`cta_response` is NULL there), pure consistency.
- **Validation, not a CHECK.** A cross-table "question's activity belongs to the survey's campaign" constraint is not expressible as a column CHECK. It is validated in the routes exactly as the survey-level rule is today (`sms-surveys/route.ts` lines 140–152; `[surveyId]/route.ts` lines 299–311) — one batched `campaign_activities` lookup over the distinct question-level ids, rejecting with `'Question N: activity not found in this campaign'`. This build-time gate is what makes the runtime's admin-client rating write safe, per the Phase 4 plan.
- **`write_rating` gating is unchanged**, so `COALESCE` can never resolve to NULL through the UI: the toggle still renders only when `value.activity_id != null` (editor lines 741–755), and the per-question override select renders **only when that toggle is on**. See the in-phase decision below.

## Notes / decisions taken in-phase

- **`fire/sms` is two-mode on one route; prepare mode writes nothing.** Rejected creating the `sms_lists` row before the picker (the literal `fire/phone` shape) because an `sms_lists` row is a blast-only artifact, Survey needs a *worker* list pinned to a draft survey instead, and there is no `DELETE` handler on `/api/campaigns/[id]/sms-lists/[listId]` to clean up the phantom draft blast. Side benefit: abandoning the picker now leaves no artifacts, where today it leaves a fired list plus an orphan draft.
- **Param name is `worker_list_id`** (not `list_id`) on `/sms/setup`, because `list_id` is already ambiguous between `campaign_worker_lists.list_id` and `sms_lists.list_id` in this module. The composer redirect keeps its existing `?sms_list=` name.
- **The Survey pathway is client-side navigation with no server write, and does not mark the source list `fired`.** `fired` means "a channel artifact was created from this cohort"; a draft survey *references* a cohort and freezes its own roll at open time. Going through the normal `POST /api/campaigns/[id]/sms-surveys` also means the survey inherits that route's validation (≥ 1 question, branch-cycle detection, activity coherence) — a fire-time direct insert could not, since the POST route rejects a question-less survey.
- **A per-channel already-fired guard is *added*, not modified.** Verified: no fire route has one today, so decision 4's "a cohort may be fired once per channel" has to be implemented from scratch. It is a 409 carrying the existing artifact id, overridable with `{ force: true }`, so the pre-existing (undocumented) ability to re-fire the same channel for a fresh list is preserved behind an explicit confirm rather than silently removed. The genuine cross-channel bug — `fire/sms` clobbering email's `fired_draft_id` — is fixed by removing that one field.
- **The real blocker to multi-channel firing was the UI, not the routes.** `useBuildList`'s lists query hardcodes `?status=draft`, so a fired list disappears from `ListPicker` and can never be selected again; `onFire`'s task branch even comments "Picker filters to draft anyway". Dropping that filter and rendering fired state per channel is what makes decision 4 usable, and is the larger half of the work.
- **`aria-pressed` becomes `aria-checked`.** A `role="menuitem"` cannot legitimately carry `aria-pressed`; the menu-native equivalent of a toggle is `role="menuitemcheckbox"` + `aria-checked`, which Radix's `CheckboxItem` provides. The toggle's *behaviour* (`handleToggleBuildList`, `?buildList=1`, `router.replace`, no navigation) is preserved byte-for-byte. This is the intended reading of decision 1's "must not lose that semantics inside a menu".
- **`onCloseAutoFocus` is required on the Build menu.** Radix returns focus to the trigger as the menu closes, which competes with `CreateAssessmentDialog` mounting. No precedent for dialog-from-dropdown exists in this codebase, so the fix ships with an explicit keyboard verification step rather than as a silent assumption.
- **Chat is disabled, not repointed.** Routing Chat at the inbox as a stand-in would create a behaviour Phase 10 then has to break, and the brief forbids it. The card is unselectable (`aria-disabled`, `tabIndex={-1}`, no handlers) and the route rejects `pathway:'chat'` as defence in depth.
- **`SmsResumeBanner` ships as a `null`-returning slot.** Assessed honestly: no SMS in-flight state is resumable this phase — there is no action/session row until Phase 10's `sms_chat_sessions`, and a `draft` `sms_lists` row is already listed in the Blasts tab and is not lost work. The slot reserves the layout position and import site; a banner that fired on draft blasts would be noise.
- **`write_rating` gating is unchanged, so `COALESCE` can never resolve to NULL through the UI.** The per-question override select renders only when the toggle is on, and the toggle renders only when the survey has a target — so a question-level target is always an *override* of a real fallback. The runtime is nevertheless made COALESCE-aware in its *gate* as well as its column, so a PostgREST-direct authoring path that sets a question target with no survey target still writes correctly rather than silently dropping ratings.
- **`activity_id` on a `write_rating: false` question is rejected**, not tolerated. Dead config that looks like a working target is worse than a validation error.
- **No Zod and no `checkRateLimit` on the fire routes.** Checked before deciding: all four `fire/*` routes hand-roll validation and none rate-limits, while the `sms-surveys` routes do use `checkRateLimit`. The phase matches each file's own neighbourhood — the `sms-surveys` route edits keep their `checkRateLimit`, the fire route edits stay bare. Zod appears nowhere in either neighbourhood, so it is not introduced.
- **`InlineSmsOpsPanel` gains a `?sms_view=` default rather than controlled tabs.** The panel only mounts when the SMS sub-tab is active, so an uncontrolled `defaultValue` derived from the URL is sufficient; a controlled-tabs refactor would touch four panels for no behavioural gain.
- **Readiness precedence is opt-out first**, matching `fire/sms`'s existing `optedOut ? 'opted_out' : phone ? 'pending' : 'skipped'` ladder, so an opted-out worker with no mobile is counted once. Sharing one pure helper between the route and the panel is what guarantees the displayed warning and the written row statuses agree.
- **`fired_email_list_id` exists and was not in the surface map.** `fire/email` writes both `fired_draft_id` (line 161) and `fired_email_list_id` (line 162); neither is in the worker-lists GET selects. Both are added to the selects and to `BuildListSummary` so per-channel fired rendering is complete rather than SMS-only.
- **Migration adds no RLS, no grants, no indexes** — two nullable FK columns on existing tables. Stated explicitly in the migration header so the migration reviewer does not have to infer the omissions.
